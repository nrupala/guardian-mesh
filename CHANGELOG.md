## [0.19.0] - 2026-11-08

### Added
- **WO-18 profile 3: operator CLI (CC-4).** The new `gm` binary is an operator client of the existing single-node daemon: it opens a handshake session, evaluates or simulates actions, verifies saved proofs and reads the audit log over gRPC. This release claims exactly WO-18 profile 3 (CC-4); the MCP surface (CC-5) is not part of it and remains target.
  - **`guardian-meshd/src/bin/gm.rs`**: hand-rolled argument parsing (no clap, matching `gm-attest`), tokio + tonic, and no new dependencies. Subcommands: `health` (full HealthResponse as JSON, status as its enum name, exit 0 for SERVING/DEGRADED), `handshake [--tenant] [--session-file]` (generates a 32-byte seed, derives the ML-DSA-65 keypair, calls Handshake as `gm-cli`, writes the session file, prints only session_id/ttl_seconds/tenant_id/session_file), `evaluate` (seals the exact camelCase ActionDescriptor JSON, HMACs it with the session key, calls Evaluate or Simulate, prints the verdict/reasons/proof summary and saves the proof envelope), `verify` (rebuilds the proto envelope from the proof file and calls VerifyProof; exit 0 valid, 1 invalid), and `audit [--limit]` (ReadAuditLog; --limit truncates the printed entries client-side only). Every subcommand accepts `--endpoint` (default `http://127.0.0.1:50051`, `GM_ENDPOINT` fallback) and `--help`; unknown flags/subcommands exit 2.
  - **Session file**: JSON with endpoint, session_id, hex session key, hex signing seed, tenant_id, created unix time and ttl_seconds. Created with mode 0600 on Unix. The session key and seed are bearer secrets and are never printed. The default path is `$HOME/.guardian-mesh/gm-session.json`; an expired session (daemon TTL, 300s) means re-running `gm handshake`.
  - **Proof file**: JSON with hex-encoded payload, payload_type, crc32c, ml_dsa_65_signature, timestamp and nonce; default `gm-proof.json` beside the session file. The evaluate -> verify flow uses exactly this file.
  - **Unit tests in `gm.rs`** (no daemon): payload field set and metadata map, session-file round-trip, proof-file round-trip, and argument-parsing errors (missing required flag, bad `--metadata` form, unknown flag) in the exit-2 class.
  - **`docs/CLI.md`**: what the CLI is and is not, build/install, every subcommand with a worked example and JSON shape, the session file and its secrets/TTL, the proof file and evaluate -> verify flow, the exit-code contract (0/1/2, BLOCK-is-success), scripting notes, and explicit non-claims.
  - Version bumped `0.18.0` -> `0.19.0` (`VERSION`, `guardian-meshd/Cargo.toml`, `README.md`, `webui/src/data/releases.ts`); the image tag in `deploy/edge/docker-compose.yaml` is `0.19.0`. The sidecar files' `0.17.0` tags are unchanged: they name the release that introduced them.
- **HONESTY BOUNDARY**: this release is a client of the existing daemon. It adds no new verdict capability, no clustering, and no daemon-logic changes. The CLI holds no policy authority: it asks the daemon like any other client, and a BLOCK verdict is a successful CLI operation (the verdict is in the JSON, not the exit code). There is no TEE attestation and no external anchoring. It is NOT forced routing (CM-4). License: Apache License 2.0 plus the Payment Rider.
- **NOT in this release**: CC-5 MCP surface remains target; no daemon behaviour change; no new verdict capability; no clustering (WO-16 DC-1/DC-3 remain open).

### Added
- **WO-18 profile 2: edge profile (DP-6).** A resource-capped, offline deployment form of the existing single-node daemon for small ARM/x86 gateways and industrial PCs. This release claims exactly WO-18 profile 2 (DP-6); the CLI (CC-4) and MCP surface (CC-5) are not part of it and remain target.
  - **`deploy/edge/guardian-meshd.service`**: systemd unit for the bare-metal/gateway form. Runs `/usr/local/bin/guardian-meshd` as a dedicated non-root `guardian` user (created with `useradd --system`), reads an optional `EnvironmentFile=-/etc/guardian-mesh/guardian-mesh.env`, works from `/run/guardian-mesh` outside the workspace (the program-dir guard requires it), and defaults `GUARDIAN_MESH_WORKSPACE=/var/lib/guardian-mesh/workspace`, `GUARDIAN_MESH_OUTPUT=/var/lib/guardian-mesh/output`, `GUARDIAN_MESH_BIND_ADDR=127.0.0.1` (loopback; `0.0.0.0` is an operator choice, never the default) and `GUARDIAN_MESH_PORT=50051`. Ceilings `MemoryMax=256M`, `CPUQuota=50%`, `TasksMax=64` are the systemd form of the DP-6 configurable ceilings, each commented as a starting value for a small gateway with measured guidance in `docs/EDGE.md` and one place to change. Hardening: `NoNewPrivileges=true`, `ProtectSystem=strict` with `ReadWritePaths=/var/lib/guardian-mesh`, `ProtectHome=true`, `PrivateTmp=true`, `Restart=on-failure`, `RestartSec=5`. No secret value in the unit; the handshake secret comes from the EnvironmentFile.
  - **`deploy/edge/guardian-mesh.env.example`**: every real `GUARDIAN_MESH_*` runtime variable an edge deployment may set, each with a one-line comment - workspace, output, bind, port, node id, policy throttle rate, escalation actions, policy admin keys, revocation bound, SPIFFE settings, OpenPGP admin keys, tenants and tenant budget/window, and degraded-mode settings. The handshake secret line carries no value, not even a placeholder literal; it is comment-only and points at deploy-time injection.
  - **`deploy/edge/docker-compose.yaml`**: the container form. One `guardian-mesh` service built from the repo `Dockerfile`, image `guardian-mesh:0.18.0`, with `mem_limit: 256m` and `cpus: 0.5` (the same starting ceilings as the systemd unit, in one place), loopback-only published port `127.0.0.1:50051:50051`, named volume `guardian-data:/data`, handshake secret passed through from the shell environment with no literal value, and `restart: unless-stopped`. Header records that this is the edge profile - resource-capped and offline, with no network egress needed or used.
  - **`docs/EDGE.md`**: documents the edge profile honestly - what it is; the systemd and container forms and when each fits; ceilings (what is configurable, where, and the statement that ceilings are enforced by systemd/the container runtime, NOT by a daemon setting, with the starting values and how to change them); offline operation (the daemon makes no outbound calls, verdicts and proof verification are fully local - no licence check, no telemetry, no update check - and no edge-to-core sync is built because BM-7 is design); persistence (`/var/lib/guardian-mesh` or `/data` holds the signing key and hash-chained audit log, and losing it loses proof continuity, WO-3); a table of every real runtime `GUARDIAN_MESH_*` variable; the fail-closed duty (no answer = BLOCK); and explicit non-claims.
  - Version bumped `0.17.0` -> `0.18.0` (`VERSION`, `guardian-meshd/Cargo.toml`, `README.md`, `webui/src/data/releases.ts`); the new image tag in `deploy/edge/docker-compose.yaml` is `0.18.0`. The sidecar files' `0.17.0` tags are unchanged: they name the release that introduced them.
- **HONESTY BOUNDARY**: this release is packaging and configuration of the existing single-node daemon. It adds no new verdict capability and no clustering (WO-16 DC-1/DC-3 remain open). NO edge-to-core sync is built (BM-7 is design): an edge guardian's proofs verify locally and travel only when an operator carries them; nothing uploads automatically. Every resource value in the shipped artifacts is a ceiling, not a measurement; the measured footprint from Wright's verification is recorded in docs/EDGE.md's release record and in Tests below. It is NOT forced routing (CM-4). There is no TEE attestation and no external anchoring (designed, not built). License: Apache License 2.0 plus the Payment Rider.

## [0.15.1] - 2026-11-03

### Fixed
- **Startup audit-chain trigger scope (Wright carry; v0.15.0 deploy defect).** v0.15.0 verified the *entire* persisted audit chain at startup and entered degraded mode when it did not verify. Deployed to production, it bricked the daemon on its own archive: the production log's 2026-10-26/27 segment interleaves two daemons' chains (concurrent writers on one workspace during the WO-11 deploy window; 89 link breaks, all inside `audit_20746.jsonl`, entries 557–668 of 2,121) and cannot verify as a single chain. v0.15.0 was rolled back to v0.14.1 the same night (box E2E 15/16, PF-18 PASS 100/15/0 after rollback). The trigger now judges the **live tail segment** only — `VaultEnclave::verify_startup_chain`: the most recent non-empty audit file's entries, chained from the previous file's last stored digest (genesis when none), with the same dual-formula entry check as `verify_chain`. Tampering with, corrupting, or forking the current segment still fails closed into degraded mode; historical segments are judged by the `ReadAuditLog` strict verification, which continues to report the 2026-10-26/27 interleave as a break (standing finding F4 of the WO-16 gate — the audit trail is append-only and is never rewritten to make it pass). Proven before deploy this time: the fixed binary run against a copy of the actual production audit log starts SERVING, and corrupting one tail byte in that copy makes it start DEGRADED with trigger `audit-chain-verification-failed`.

## [0.15.0] - 2026-11-03

### Added
- **WO-16 v1: Declared degraded modes (DC-4/DC-5) and issuing node identity (DC-2).** A daemon can be started in a declared degraded mode with a pre-declared safe-action subset, and proofs now name the node that issued them. Multi-node consensus (DC-1) and threshold issuance (DC-3) are NOT in this release and remain target: v1 is single-node and does not add cluster networking or threshold issuance.
  - **Config (`guardian-meshd/src/config.rs`)**: `node_id: Option<String>` from env `GUARDIAN_MESH_NODE_ID`; `degraded: bool` from env `GUARDIAN_MESH_DEGRADED` ("1"/"true"); `degraded_safe_actions: Vec<String>` from env `GUARDIAN_MESH_DEGRADED_SAFE_ACTIONS` (comma-separated, trimmed, empties dropped, parsed like the escalate-actions list). All three wired into `Default::default()`.
  - **Degraded module (`guardian-meshd/src/degraded.rs`, new)**: `DegradedState { active, trigger, safe_actions, since_unix }` with `inactive()`, `active(trigger, safe_actions, since_unix)`, and `allows(action_type)` (true when not active, or when the action is in the pre-declared subset by exact match). Unit tests cover inactive-allows-all, active-empty-subset-allows-nothing, and active-subset-allows-only-named-actions.
  - **Vault event (`guardian-meshd/src/enclave/vault.rs`)**: `record_degraded_event(event, trigger)` appends a hash-chained audit entry following the certificate-event locking/persist discipline: action_id = hex of `DEGRADED_MODE`, verdict = the event string (`DEGRADED_MODE_ENTERED` / `DEGRADED_MODE_EXITED`), reason = `trigger=<trigger>`.
  - **Proto (additive only)**: `AuditProof` gains `string issuing_node = 9;`. `HealthResponse` gains `string node_id = 10; bool degraded = 11; string degraded_trigger = 12; repeated string degraded_safe_actions = 13; uint64 degraded_since_unix = 14;`.
  - **Service (`guardian-meshd/src/main.rs`)**: `GuardianMeshService` gains `node_id: String` and `degraded: DegradedState`. At startup, after the signing key is loaded, node_id resolves from `GUARDIAN_MESH_NODE_ID` when non-empty, otherwise `node-<first 12 hex chars of the signing-key fingerprint>`. After vault creation the daemon verifies the persisted audit chain; a completed verification that reports an invalid chain triggers `audit-chain-verification-failed`, while a read error on a fresh/empty workspace does not. Operator-declared degradation (`GUARDIAN_MESH_DEGRADED`) takes precedence with trigger `operator-declared`. On entering degraded mode the daemon records `DEGRADED_MODE_ENTERED` (audit failure logged to stderr, never fatal) and writes `<workspace>/degraded.marker` containing the trigger. On a later clean startup with the marker present it records `DEGRADED_MODE_EXITED` for the marker's trigger and removes the marker. Every `AuditProof` construction site (including the new DC-4 block) carries `issuing_node`. In `run_evaluation`, immediately after tenant and action resolution and before the tenant-policy decision, an action outside the safe subset returns a sealed BLOCK with rule_id `DC-4`, verdict `BLOCK`, the failure-closed reason naming the trigger and action, remediation naming `GUARDIAN_MESH_DEGRADED_SAFE_ACTIONS`, and a real-only tenant audit append; it consumes no tenant budget. Health reports `DEGRADED` while active and fills node_id, degraded, trigger, safe actions, and since_unix.
  - **Docs**: new `docs/DEGRADED_MODES.md` documenting the declared-mode contract: triggers, safe-subset configuration, fail-closed behaviour, entry/exit audit events and marker, exit procedure (remove the trigger and restart), and explicit non-claims (no cluster consensus in v1).
  - Version bumped `0.14.1` → `0.15.0` (`VERSION`, `guardian-meshd/Cargo.toml`, `README.md`, `webui/src/data/releases.ts`).

## [0.8.0] - 2026-10-19

### Added
- **WO-6: Release-evidence certification (GMSI-1).** Guardian Mesh can now issue certificates that bind a gate verdict to an evidence pack under the daemon's cryptographic signature. This is Guardian Mesh's first certificate issuance capability.
  - **Certificate schema v1** (`specs/CERTIFICATE_SCHEMA.md`): A certificate is a sealed envelope (the existing `SealedEnvelope` wire format) carrying a structured JSON body. The certificate attests to the binding between a specific release artifact (identified by its SHA-256 evidence hash), the gate verdict issued over that evidence, test results and policy declared by the presenter, the issuing daemon's identity (its signing-key fingerprint from WO-3), and the issuance timestamp. All fields needed to verify a certificate travel inside the sealed envelope (GMSI-3: self-contained; verifiable by a second lane through the existing `VerifyProof` RPC).
  - **Three new RPCs**: `IssueCertificate`, `RevokeCertificate`, `CertificateStatus`. Issuance enforces all rules in the specification:
    - The daemon computes SHA-256 over the presented evidence bytes and refuses issuance if it does not match the claimed hash (GMSI-2: hash-verifiable handoff).
    - Evidence size cap: **10 MB**. Evidence packs larger than this are refused with a clear error. (This is separate from the 64 KiB `SealedEnvelope` cap, which applies to envelopes, not evidence documents.)
    - `verdict == "BLOCKED"` → NO issuance. If an ACTIVE certificate exists for that product+version, it is REVOKED (registry + audit log), and the refusal message states that revocation occurred.
    - `verdict == "PASS"` or `verdict == "PASS WITH FINDINGS"` → issue the certificate. Assign a unique serial (persistent across restarts), build the body, seal it with the daemon's persistent signing key (WO-3), persist the registry record as ACTIVE, append the issuance event to the audit log. Any previously ACTIVE certificate for the product (any version) becomes SUPERSEDED, and the new certificate's `supersedes` field names the old serial.
    - Any other verdict string → refusal (clear error, nothing recorded).
  - **Lifecycle management**: Certificates have four states (ACTIVE, SUPERSEDED, REVOKED, UNKNOWN). Issuance, supersession, and revocation events are appended to the daemon's hash-chained audit log (the WO-4/WO-6 audit trail). The certificate registry persists under the daemon's workspace directory (following the WO-3 persistence pattern) and survives restarts.
  - **Verification**: A certificate holder verifies a certificate by (1) presenting the sealed envelope to `VerifyProof` (any Guardian Mesh daemon can verify the ML-DSA-65 signature), (2) recomputing the fingerprint (SHA-256 of the exact payload bytes) and verifying it matches the fingerprint presented alongside the envelope in the `IssueCertificate`/`CertificateStatus` responses — the fingerprint is not a field inside the sealed payload (GMSI-2: the copy presented, not the copy at mint), and (3) querying `CertificateStatus(serial)` to verify the certificate is ACTIVE (not SUPERSEDED or REVOKED).
  - **Trust posture (v1)**: Issuance is a daemon-local operation. The daemon binds to localhost (or sits behind access control, as the production deployment does). There is no public issuance endpoint in v1. The issued certificate can be presented to **any** Guardian Mesh daemon for verification via `VerifyProof`.
  - **Honesty clauses**: The certificate certifies the **binding** (this evidence, this verdict, this issuer, this time), not the truth of the declarations. The daemon vouches for: the evidence hash match at issuance, the signature, the lifecycle state transitions it performed, and the issuer identity. The daemon does NOT vouch for: the truth of the `scope`, `tests`, or `policy` declarations (these are the presenter's claims, bound under the daemon's signature), or deployment choices / runtime behavior / operational posture. A certificate warrants only the exact artifact tested (identified by `evidence_hash`), against the policy named (`policy`), on the date stamped (`issued_at`).
  - **GMSI-5: History scope**. The certificate schema includes an `evidence_scope` field: `"working-tree"` (only the working tree was scanned) or `"full-history"` (the full git history was scanned). A secret ever committed stays in git history; certification of a repository must state whether history was scanned, not only the working tree.
  - **GMSI-7 (reserved)**: The certificate schema reserves a `pf_outcomes` field for future use. In v1, this field is `null` and MUST NOT carry placeholder or constant values. Future versions (after WO-19 lands) will populate this field with the daemon's measured per-rule Protocol Firewall pass/fail counts at issuance time.

The Gatekeeper checks the policy rate first, then PF-18, and both use independent rate limiters per session.
  - **ESCALATE verdict** is emitted for action types on a policy-configured escalation list (`GUARDIAN_MESH_POLICY_ESCALATE_ACTIONS` environment variable, comma-separated, defaults to empty). Actions on the list (and not blocked by policy) return verdict "ESCALATE" with a reason naming the matched action type. **Precedence is pinned**: an action type the policy blocks still returns BLOCK; an action type on the escalate list (and not blocked) returns ESCALATE; everything else follows the existing policy unchanged. The proof envelope is issued for ESCALATE like any verdict, and the audit log records the escalation.
  - **Panel changes**: The control panel (`DashboardPage.tsx`) now renders THROTTLE and ESCALATE verdicts distinctly with their own styles (orange/amber, matching the existing CSS classes `verdict-throttle` and `verdict-escalate`) alongside ALLOW (green) and BLOCK (red). Verdict tags in the audit log and the live verdict panel display THROTTLE and ESCALATE with plain-language descriptions: THROTTLE means "the action is slowed down"; ESCALATE means "a human decides". The CSS for these verdict styles was already present in `index.css` from a previous iteration; this release wires them to real verdicts.

### Changed
